# Security

## Threat model

| Attacker | Goal | Control |
| --- | --- | --- |
| Self-promoting developer | Fake rating, views or downloads | Server-owned counters; rules reject the fields; aggregates recomputed from source events |
| Developer | Skip moderation and go live | `status` transitions restricted; only a callable with an admin claim can approve |
| Advertiser | Free impressions, or inflate spend to hurt a competitor | Impressions counted server-side at serve time, deduped per user per hour; budget debited by the function, not the client |
| Advertiser | Pay ₹1 for ₹10,000 of budget | Amount validated against platform limits in `createRazorpayOrder`; budget credited only by a signed webhook |
| Curious user | Read another user's email, drafts, notifications | Field-level rules; `private/` subcollections; recipient-only notifications |
| Compromised client | Forge a role | Roles come from custom claims written only by `setUserRole`; rules never read a client-supplied `role` |
| Bot | Scrape the catalogue, spam reviews | App Check on every request; one review per user per app by document id; rate limits on callables |

## Three independent gates for privileged actions

1. **Router** - `/admin` redirects non-admins away (cosmetic, fast feedback).
2. **Screen** - `AdminScreen` re-checks `isAdminProvider` before rendering.
3. **Server** - every mutation is a callable that calls `requireAdmin(request)`,
   which reads `request.auth.token.role`. A forged client passes gates 1 and 2
   and still fails here.

## Rules walkthrough (`firestore.rules`)

Helpers at the top: `signedIn()`, `uid()`, `role()`, `isAdmin()`,
`onlyChanged(keys)`, `unchanged(keys)`. Everything is deny-by-default; the final
catch-all `match /{document=**} { allow read, write: if false; }` means a new
collection is private until someone writes a rule for it.

Highlights:

- **Listings.** Create requires `ownerId == uid()` *and* every server-owned
  counter to be zero, so nobody can seed social proof. Owner updates are checked
  against a whitelist of changed keys; `rating`, `viewCount`, `sponsored`,
  `featured` and `moderation` may never appear in a client diff. Status may only
  move along the allowed edges.
- **Reviews.** The document id must equal `applicationId + '_' + uid`, the
  rating must be 1-5, and a `get()` on the application rejects self-reviews.
- **Bookmarks / follows.** Composite ids make "bookmark someone else's row"
  structurally impossible: the id must start with the caller's uid.
- **Campaigns.** Creation requires the caller to own the advertised application
  (checked with `get()`), zero delivery counters, and a budget above the floor.
  After approval, budget, targeting and objective are frozen.
- **`campaign_events`, `notifications`, `admin_audit_logs`, `payments`** are
  function-only. There is no client write path at all.
- **Users.** `role`, `isDeveloper` and the counters are excluded from owner
  updates by an `unchanged()` assertion.

## Storage rules

Ownership is resolved against Firestore with `firestore.get()`, so the rule
agrees with the database rather than trusting a path segment. Uploads made before
a draft exists stage under the owner's uid (`app_icons/{uid}/…`), which
`ownsStaging()` permits only for that user - otherwise the very first icon upload
of a new listing would fail, because there is no application document to check. Every write is
capped by size and content type (`image/png|jpeg|webp`), and public read is
limited to marketing assets - avatars, icons, screenshots, banners, creatives.

## Secrets

| Secret | Where it lives |
| --- | --- |
| `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Secret Manager, bound to the payment functions |
| `RAZORPAY_KEY_ID`, `STRIPE_PUBLISHABLE_KEY` | Build-time `--dart-define` (publishable by design) |
| Firebase service account | Never in the repository; `initializeApp()` uses the runtime identity |
| `lib/core/config/firebase_options.dart` | Generated by the CLI, git-ignored |

`AppConfig` reads only `--dart-define` values, so there is no file in `lib/` that
can leak a credential. `.gitignore` also blocks `google-services.json`,
`GoogleService-Info.plist` and `functions/.env`.

## Release signing

The release APK is signed with a keystore that never enters the repository:

| Item | Where it lives |
| --- | --- |
| `upload-keystore.jks` | `android/app/`, git-ignored; in CI decoded from `ANDROID_KEYSTORE_BASE64` |
| `android/key.properties` | git-ignored, `chmod 600`, written by `tool/configure_signing.sh` |
| Passwords, alias | GitHub Actions secrets (`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD`, `ANDROID_KEY_ALIAS`) |

`tool/configure_signing.sh` injects a `signingConfigs.release` block into
`android/app/build.gradle(.kts)` and **removes the template's
`signingConfig = signingConfigs.debug` line** - leaving it would silently sign a
release build with the debug key, which Play rejects and which breaks the
upgrade path for anyone who installed an earlier build.

Losing the keystore means losing the ability to update the app. Back it up
outside the repository, in a password manager or a secret store, and keep the
passwords separate from it.

`flutter build apk --release` is never run unsigned: the CI workflow fails loudly
if `ANDROID_KEYSTORE_BASE64` is missing, and verifies the produced APK with
`apksigner verify --print-certs` before uploading it.

## Payment integrity

The client never computes an amount. `createRazorpayOrder` re-validates the
requested amount, creates the order with the secret key, and stores a `payments`
row. The capture path is the **webhook**: HMAC-verified (Razorpay) or
signature-verified (Stripe), idempotent (a second delivery returns "already
processed"), and the only writer of `budget`. A client that reports success it
did not earn changes nothing.

## Advertising integrity

- Impression counting happens inside `serveAds`, at the moment the ad is served.
- The impression ledger id is `campaignId_uid_hour`, so one person cannot
  generate more than one billed impression per campaign per hour.
- `trackCampaignEvent` refuses clicks on campaigns that are not `active`, and
  records zero cost for clicks (billing is per impression).
- Daily delivery is capped by `LIMITS.dailyCapRatio`; a campaign that exhausts
  its budget flips to `exhausted` in the same transaction.

## App Check

`bootstrap.dart` activates App Check before any Firestore read. Debug builds use
the debug provider; production uses Play Integrity on Android and DeviceCheck on
iOS. Enforce App Check for Firestore, Storage and Functions in the console once
your clients are updated, otherwise requests without attestation are refused.

## What is intentionally not defended here

- **Screenshot plagiarism** needs perceptual hashing or human review; moderation
  catches the obvious cases.
- **Review bombing** by many accounts is a policy problem, not a rules problem.
  The reports queue plus `suspended` status is the lever.
- **Full-text search abuse** does not apply: search is prefix + keyword only.
